# アーキテクチャ設計書（X風SNS）

要件は [requirements.md](requirements.md) を参照。

## 1. 方針まとめ

| 項目 | 決定 |
|------|------|
| バックエンド言語 | **Go**（素のPythonは不採用。理由は2章） |
| バックエンド構造 | レイヤードアーキテクチャ |
| API仕様 | OpenAPI 3.0（`api/openapi.yaml`）。仕様を先に書き、コードを生成する |
| フロントエンド | TypeScript + React + Vite（SPA）。OpenAPIから型付きクライアントを生成する |
| データベース | PostgreSQL |
| 画像保存 | S3互換ストレージ（開発時はローカルディスク） |

## 2. 言語選定：素のPythonは可能か

**結論：実用上は無理と判断し、Goを採用する。**

「素のPython」は標準ライブラリのみ（外部パッケージなし）と解釈した。動かすこと自体はできるが、このSNSの要件では次の点で足りない。

| 要件 | 標準ライブラリのみの場合 | 判定 |
|------|--------------------------|------|
| PostgreSQL接続 | 標準にドライバがない（`sqlite3`のみ） | ✗ |
| 画像アップロード（multipart） | `cgi`モジュールがPython 3.13で削除済み。自前でパースする必要がある | ✗ |
| 同時接続の処理 | `http.server`は本番用ではない。`wsgiref`も開発用 | ✗ |
| パスワードハッシュ | `hashlib.scrypt`は使える（bcrypt / argon2はない） | △ |
| ルーティング、入力検証、レート制限 | すべて自作 | △ |
| OpenAPIとの連携 | 仕様の検証・コード生成ツールが標準にない。手書きで二重管理になる | ✗ |

PostgreSQLをやめてSQLiteにし、`http.server`を使えば動く。ただし、上の表のうち複数を自作することになり、「OpenAPI駆動」と「本番運用」の両方を満たしにくい。

**Goを選ぶ理由**
- `net/http`（Go 1.22以降はメソッド・パスパターン対応）、`database/sql`、`mime/multipart`が標準で揃い、本番でそのまま動く。
- OpenAPIからのコード生成（oapi-codegen）が成熟している。
- 型付きで、レイヤー間の依存をインターフェースで表現しやすい。
- 単一バイナリで配置でき、EC2などへのデプロイが簡単。
- 同じ `project` 内の `newsSite/backend` もGoで、`cmd` / `internal` 構成を使っている。

## 3. 全体構成

```
[ブラウザ]
   │ HTTPS
   ▼
[リバースプロキシ (Caddy / nginx)] ── /api/* ─▶ [Go APIサーバー] ─▶ [PostgreSQL]
   │                                                 │
   └─ 静的ファイル (React ビルド)                    └─▶ [画像ストレージ (S3互換)]
```

- フロントは静的ファイルとして配信し、APIは `/api/v1` 配下に置く。
- 同一オリジンで配信するため、CORSの設定が不要になる。

## 4. バックエンド：レイヤードアーキテクチャ

### 4.1 レイヤー

```
┌──────────────────────────────┐
│ handler      （プレゼンテーション） │ HTTPの入出力、入力検証、認証情報の取り出し
├──────────────────────────────┤
│ usecase      （アプリケーション）   │ ユースケースの手順、トランザクション境界
├──────────────────────────────┤
│ domain       （ドメイン）          │ エンティティ、ルール、リポジトリのインターフェース
├──────────────────────────────┤
│ repository   （インフラ）          │ DBアクセス、外部ストレージ、メール送信の実装
└──────────────────────────────┘
```

**依存の向き**：`handler → usecase → domain ← repository`

- 上のレイヤーから下のレイヤーへだけ呼び出す。
- `repository`は`domain`が定義したインターフェースを実装する（依存関係逆転）。そのため`usecase`はDBの種類を知らない。
- `handler`が`repository`を直接呼ぶことは禁止する。

### 4.2 各レイヤーの責務

| レイヤー | やること | やらないこと |
|----------|----------|--------------|
| handler | リクエストの解析、形式検証、レスポンス生成、エラーのHTTPステータス変換 | 業務ルールの判断、SQL |
| usecase | 「投稿する」「フォローする」などの手順、権限チェック、トランザクション制御 | HTTPの知識、SQL |
| domain | 文字数上限などの不変条件、エンティティ、リポジトリのインターフェース | 他レイヤーのimport |
| repository | SQLの実行、画像の保存、`domain`のエンティティへの変換 | 業務ルールの判断 |

### 4.3 ディレクトリ構成

既存の `backend/` に次の構成で作る。

```
backend/
├── cmd/
│   └── server/
│       └── main.go            # 起動、依存の組み立て（DI）
├── internal/
│   ├── handler/               # プレゼンテーション層
│   │   ├── post_handler.go
│   │   ├── user_handler.go
│   │   └── ...
│   ├── middleware/            # 認証、ログ、レート制限、CSRF
│   ├── usecase/               # アプリケーション層
│   │   ├── post_usecase.go
│   │   └── ...
│   ├── domain/                # ドメイン層
│   │   ├── user.go
│   │   ├── post.go
│   │   └── repository.go      # インターフェース定義
│   ├── repository/            # インフラ層
│   │   ├── postgres/
│   │   └── storage/
│   ├── gen/                   # OpenAPIから生成したコード（手編集しない）
│   └── config/                # 環境変数の読み込み
├── migrations/                # DBマイグレーション（SQL）
├── go.mod
└── go.sum
```

### 4.4 処理の流れ（例：投稿作成）

1. `middleware`がセッションを検証し、ユーザーIDをコンテキストに入れる。
2. `handler`がJSONを解析し、`usecase.CreatePost(userID, body)`を呼ぶ。
3. `usecase`が`domain.NewPost`で文字数などを検証し、`PostRepository.Create`を呼ぶ。
4. `repository`がSQLを実行して保存する。
5. 結果を`handler`がレスポンス用の形に変換して返す。

### 4.5 エラーの扱い
- `domain`で業務エラーを定義する（例：`ErrNotFound`、`ErrForbidden`、`ErrValidation`）。
- `handler`で一箇所に集約してHTTPステータスへ変換する（400 / 401 / 403 / 404 / 409 / 500）。
- 予期しないエラーはログに詳細を残し、レスポンスには内部情報を出さない。

### 4.6 なぜレイヤードアーキテクチャか

#### 採用理由

| 理由 | 内容 |
|------|------|
| 関心事を分けられる | 「HTTPの扱い」「業務の手順」「DBの扱い」を別々の場所に書く。変更の影響範囲が狭くなる |
| テストしやすい | `usecase` はリポジトリのインターフェースだけを知っている。DBなしでモックに差し替えて試せる |
| 変更に強い | DBの変更やAPIの形式変更が、他のレイヤーに波及しにくい |
| 規模に合っている | このSNSは機能が多いが、一つの運営主体が作る一つのアプリである。複雑な構造は不要 |
| 学びやすい | 名前と役割が直感的で、初学者でも「どこに何を書くか」を判断しやすい |
| チーム開発に向く | レイヤーごとに分担でき、新しく入った人も構造を理解しやすい |

#### 他の選択肢と比較した理由

| 候補 | 特徴 | 不採用の理由 |
|------|------|--------------|
| 単純なMVC／1ファイルに全部書く | 最初は速い | 機能が増えるとハンドラにSQLと業務ルールが混ざる。テストが難しくなる |
| クリーンアーキテクチャ／ヘキサゴナル | 依存の制御がより厳密 | 本質はレイヤードと近い。ファイル数と抽象化が増え、この規模では見合わない。**レイヤード + 依存関係逆転**で、必要な部分は取り入れている |
| DDD（ドメイン駆動設計）の本格適用 | 複雑な業務ルールの整理に強い | SNSの業務ルールは比較的単純（文字数、権限程度）。集約や境界づけられたコンテキストは過剰 |
| マイクロサービス | 独立してスケール・デプロイできる | 運用が複雑になる。初期は1つのサービス（モジュラーモノリス）で十分 |

#### 注意点（弱点）

- 単純な処理でも、複数のレイヤーを経由するため、**ファイルが増える**。たとえば「いいね」の追加でも handler・usecase・repository の3か所を触る。
- `usecase` が単に `repository` を呼ぶだけの薄い層になることがある。その場合も、権限チェックなどを置く場所として維持する。
- ルールを守らないと崩れる。「handler から repository を直接呼ばない」ことは、コードレビューで確認する。
- 規模が大きくなり、機能ごとの独立性が必要になったら、**機能単位（投稿、ユーザー、通知など）でパッケージを分ける**ことを検討する。

## 5. OpenAPI

- 仕様書は **`api/openapi.yaml`** に置く（既存の `api/` ディレクトリを使う）。
- **仕様を先に書く（スキーマファースト）**。実装は仕様に従う。
- ツール

  | 用途 | ツール |
  |------|--------|
  | Goのサーバー側コード生成 | oapi-codegen（インターフェースと型を `internal/gen` に出力） |
  | TypeScriptの型・クライアント生成 | openapi-typescript + openapi-fetch |
  | 仕様の静的検証 | Spectral（CIで実行） |
  | ドキュメント表示 | Swagger UI または Redoc |

- 生成コードはコミットし、手で編集しない。仕様を変えたら再生成する。
- CIで「仕様と生成コードに差分がない」ことを確認する。

### 5.1 API規約
- ベースパス：`/api/v1`
- 形式：JSON。画像アップロードのみ `multipart/form-data`。
- 認証：セッションCookie（`HttpOnly` / `Secure` / `SameSite=Lax`）。
- 一覧取得：カーソル方式（`?cursor=...&limit=20`）。タイムラインは追加が頻繁なため、オフセット方式は使わない。
- エラー形式：`{ "code": "validation_error", "message": "...", "details": [...] }`

### 5.2 エンドポイント案

| 分類 | メソッドとパス |
|------|----------------|
| 認証 | `POST /auth/register`、`POST /auth/login`、`POST /auth/logout`、`POST /auth/password-reset` |
| ユーザー | `GET /users/{handle}`、`PATCH /users/me`、`DELETE /users/me` |
| フォロー | `PUT /users/{handle}/follow`、`DELETE /users/{handle}/follow`、`GET /users/{handle}/followers`、`GET /users/{handle}/following` |
| 投稿 | `POST /posts`、`GET /posts/{id}`、`DELETE /posts/{id}`、`GET /posts/{id}/replies` |
| タイムライン | `GET /timeline/home`、`GET /timeline/global` |
| 反応 | `PUT /posts/{id}/like`、`DELETE /posts/{id}/like`、`PUT /posts/{id}/bookmark`、`DELETE /posts/{id}/bookmark` |
| 検索 | `GET /search/users`、`GET /search/posts` |
| 通知 | `GET /notifications`、`POST /notifications/read` |
| 通報・管理 | `POST /reports`、`GET /admin/reports`、`POST /admin/users/{id}/suspend` |
| 画像 | `POST /media` |

## 6. フロントエンド

「任せる」とのことなので、次の構成で進める。

| 項目 | 採用 | 理由 |
|------|------|------|
| 言語・FW | TypeScript + React + Vite | SPAで十分。ログイン前提の画面が中心で、SSRの必要性が低い |
| API通信 | openapi-fetch（生成された型を使用） | 仕様とフロントの型が常に一致する |
| サーバー状態 | TanStack Query | タイムラインの取得・キャッシュ・無限スクロールに向く |
| ルーティング | React Router | 画面一覧の遷移に対応 |
| スタイル | Tailwind CSS | レスポンシブ対応が書きやすい |
| テスト | Vitest + Testing Library | |

ディレクトリは `frontend/src/{pages,components,features,api,hooks}` を基本にする。`api/` に生成クライアントを置く。

## 7. データベース

- PostgreSQL。マイグレーションは `backend/migrations/` にSQLファイルで管理する（golang-migrate）。
- 主なテーブルは要件定義書の「5. 主なデータ」を参照。
- インデックス
  - `posts(user_id, created_at DESC)`：プロフィールの投稿一覧
  - `follows(follower_id, followee_id)`：ホームタイムライン
  - `likes(post_id)`、`notifications(user_id, created_at DESC)`
- ホームタイムラインは、初期は「フォロー中ユーザーの投稿をクエリで取得」する（pull型）。規模が大きくなってから、事前に書き込む方式（push型）へ移行を検討する。
- 投稿の削除は論理削除（`deleted_at`）にする。

## 8. セキュリティ

| 項目 | 対策 |
|------|------|
| パスワード | argon2id でハッシュ化 |
| セッション | サーバー側で管理。ログイン時にIDを再発行する |
| CSRF | `SameSite=Lax` に加え、状態変更APIはカスタムヘッダーまたはトークンで確認する |
| XSS | 投稿本文はエスケープして表示する。CSPを設定する |
| SQLインジェクション | プレースホルダ（パラメータ化クエリ）のみ使う |
| レート制限 | ログイン、登録、投稿、画像アップロードに設定する |
| 画像 | 拡張子ではなく中身で形式を判定する。サイズ上限を設ける。EXIF（位置情報）は削除する |
| 認可 | 「自分のリソースか」の判定は `usecase` 層で必ず行う |

## 9. テスト戦略

| 対象 | 種類 | 方針 |
|------|------|------|
| domain | 単体テスト | 外部依存なし。ルールを網羅する |
| usecase | 単体テスト | リポジトリをモックにして検証する |
| repository | 結合テスト | 実際のPostgreSQL（Docker）で実行する |
| handler | APIテスト | `httptest` でリクエスト〜レスポンスを検証する |
| 全体 | E2E | 主要シナリオ（登録→投稿→フォロー→タイムライン）のみ |

## 10. 開発・運用

- ローカル：Docker Compose（PostgreSQL、API、フロント開発サーバー）
- CI：lint、テスト、OpenAPIの検証、生成コードの差分チェック
- 設定：環境変数で渡す（`.env` はコミットしない）
- ログ：構造化ログ（JSON）。リクエストIDを付与する
- 配置：単一バイナリ + 静的ファイルを、リバースプロキシ経由で配信する

## 11. 未決事項

- セッションの保存先（PostgreSQLのテーブルか、Redisか）。初期はPostgreSQLで足りる想定。
- 画像の配信方法（CDNを使うか）。
- 全文検索（投稿検索）を PostgreSQL の機能で行うか、検索エンジンを別に立てるか。
- メール送信サービス（パスワード再設定用）。

# 付録：初学者向け解説

ここから先は、Webアプリの作り方に慣れていない人向けの説明である。

## A. まず全体像：Webアプリは何をしているか

SNSで「投稿」ボタンを押したとき、裏では次のことが起きる。

```
ブラウザ（画面）  ──「この文章を投稿して」──▶  サーバー（バックエンド）  ──保存──▶  データベース
                  ◀──「できたよ」──────────                ◀────────────
```

- **フロントエンド**：ユーザーが見る画面。ボタンや入力欄を表示する。
- **バックエンド**：画面の裏で動くプログラム。ルールを確認し、データを保存・取得する。
- **データベース（DB）**：データを長期間しまっておく倉庫。
- **API**：フロントエンドとバックエンドがやり取りするための「窓口のルール」。「投稿を作る」「投稿一覧をください」といった依頼の形式を決めたもの。

## B. レイヤード（層状）アーキテクチャとは

**役割ごとにプログラムを層に分ける**設計である。レストランにたとえると分かりやすい。

| レストラン | プログラム上の名前 | 仕事 |
|-----------|-------------------|------|
| ホール係 | **handler**（ハンドラ） | お客さん（ブラウザ）から注文を聞き、料理を届ける。調理はしない |
| 料理長 | **usecase**（ユースケース） | 注文を受けて、どの手順で作るかを決める |
| レシピと決まり | **domain**（ドメイン） | 「この料理にはこの材料を使う」などの基本ルール |
| 倉庫番 | **repository**（リポジトリ） | 材料（データ）の出し入れをする。倉庫（DB）の中身を知っている |

ホール係が倉庫に直接材料を取りに行くと、店が混乱する。だから**「ホール係は料理長に頼む」「料理長が倉庫番に頼む」と、順番を決めておく**。これが層に分ける意味である。

```
 お客さん → ホール係(handler) → 料理長(usecase) → 倉庫番(repository) → 倉庫(DB)
                                      │
                                 レシピ(domain) を参照
```

### 各層で何を書くか（「投稿する」を例に）

**1. handler：リクエストを受け取る。**

```go
func (h *PostHandler) Create(w http.ResponseWriter, r *http.Request) {
    // ① 送られてきたJSONを読む
    var req CreatePostRequest
    json.NewDecoder(r.Body).Decode(&req)

    // ② ログイン中のユーザーIDを取り出す
    userID := UserIDFromContext(r.Context())

    // ③ 実際の処理は usecase に任せる
    post, err := h.usecase.CreatePost(r.Context(), userID, req.Body)

    // ④ 結果をJSONで返す
    writeJSON(w, post)
}
```

**2. usecase：手順を組み立てる。**

```go
func (u *PostUsecase) CreatePost(ctx context.Context, userID int64, body string) (*Post, error) {
    // ルールに合った投稿を作る（文字数チェックは domain 側）
    post, err := domain.NewPost(userID, body)
    if err != nil {
        return nil, err
    }
    // 保存は repository に頼む
    return u.posts.Create(ctx, post)
}
```

**3. domain：基本のルールを持つ。**

```go
func NewPost(userID int64, body string) (*Post, error) {
    if utf8.RuneCountInString(body) > 140 {
        return nil, ErrValidation // 140文字を超えたらエラー
    }
    return &Post{UserID: userID, Body: body}, nil
}

// 「こういう保存の仕方ができる窓口が必要」という約束だけを書く
type PostRepository interface {
    Create(ctx context.Context, p *Post) (*Post, error)
}
```

**4. repository：DBに保存する。**

```go
func (r *PostgresPostRepository) Create(ctx context.Context, p *domain.Post) (*domain.Post, error) {
    // SQL を実行するのはここだけ
    row := r.db.QueryRowContext(ctx,
        "INSERT INTO posts (user_id, body) VALUES ($1, $2) RETURNING id, created_at",
        p.UserID, p.Body)
    err := row.Scan(&p.ID, &p.CreatedAt)
    return p, err
}
```

> 上のコードは考え方を示すための簡略版で、実際に動くコードではない。

## C. 層を分けると何が嬉しいか

- **直しやすい**：文字数の上限を140から280文字へ変えるときは、`domain` だけを見ればよい。
- **試しやすい**：`usecase` のテストでは、本物のDBの代わりに「保存したふりをする偽物」を渡せる。DBを用意しなくても素早く確認できる。
- **取り替えやすい**：DBの種類を変えても、`repository` だけを書き換えればよい。

## D. 「インターフェース」と「依存関係逆転」

初学者がつまずきやすい部分なので、少し丁寧に説明する。

**インターフェース**は「こういう操作ができること」という約束事である。コンセントの形のようなもので、家電（`usecase`）は、壁の中の配線（DBの種類）を知らなくても、コンセントの形さえ合えば使える。

`usecase` が `repository` の実装（PostgreSQL用のコード）を直接 import すると、`usecase` がDBの種類に縛られる。そこで次のようにする。

1. `domain` に「`PostRepository` という約束（インターフェース）」を書く。
2. `usecase` はその約束だけを知っている。
3. `repository` が約束を満たす実装を提供する。
4. 起動時（`main.go`）に、実際の実装を `usecase` に渡す（これを **DI＝依存性の注入** という）。

こうすると矢印が「`repository` → `domain`」の向きになる。普通の考え方と**逆向き**なので「依存関係逆転」と呼ぶ。

## E. OpenAPIとは

APIの仕様（どんな依頼を送れて、どんな返事が来るか）を、**決まった書式のファイル（YAML）に書いたもの**である。

```yaml
/posts:
  post:
    summary: 投稿を作成する
    requestBody:
      content:
        application/json:
          schema:
            properties:
              body: { type: string, maxLength: 140 }
    responses:
      "201": { description: 作成した }
      "400": { description: 入力が不正 }
```

嬉しい点は次のとおり。

- 仕様書を元に、**バックエンドとフロントエンドのコードの一部を自動生成**できる。
- 手で書く場合に起きがちな「画面とAPIで認識がずれる」ミスを減らせる。
- 見やすいAPIドキュメントも自動で作れる。

## F. このドキュメントに出てくる用語集

| 用語 | 意味 |
|------|------|
| ミドルウェア | リクエストが handler に届く前に共通で行う処理（ログイン確認、ログ出力など） |
| セッション | 「ログイン中である」ことをサーバー側で覚えておく仕組み |
| トランザクション | 複数のDB操作を「全部成功するか、全部なかったことにするか」にまとめる仕組み |
| マイグレーション | DBのテーブル構造を変更する手順を、ファイルとして記録・管理すること |
| モック | テスト用の「ふりをする偽物」 |
| CORS | ブラウザが、別のサイトのAPIを呼び出してよいかを制御する仕組み。同一オリジンなら問題にならない |
| CSRF | ログイン中のユーザーを騙して、意図しない操作をさせる攻撃 |
| XSS | 悪意あるスクリプトを画面に埋め込む攻撃 |
| ハッシュ化 | 元に戻せない形に変換すること。パスワードはこの形で保存する |
| スキーマファースト | 実装より先にAPI仕様（スキーマ）を書く進め方 |
| DI（依存性の注入） | 必要な部品を、外から渡して使わせる方法 |

## G. 実装を進める順番（初学者向けの目安）

1. 「投稿を1件作って、保存して、取り出す」だけを、handler → usecase → repository の順に作る。
2. その1機能が動いたら、同じ形を「ユーザー登録」「ログイン」「フォロー」へ広げる。
3. 動くものができてから、テストや細かいセキュリティ対策を足す。

最初から全機能の設計を完璧にしようとしない。**小さく作って、層の役割を体で覚える**のが近道である。
